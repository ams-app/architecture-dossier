SH.01 Contexte système

AMS tourne dans le réseau local du client, pas dans le cloud

Contrainte structurante depuis la Partie 1 (Vision) : on-premise, aucune donnée d'audit chez un tiers. Le seul flux sortant est l'email (SMTP local ou relais du client) pour les codes OTP et futures relances. Les mises à jour arrivent en tirant une image versionnée, jamais en installant depuis une source externe non maîtrisée.

SH.02 Conteneurs & stack

Trois conteneurs, un réseau Docker, pas de service SaaS tiers

SH.04 Deux architectures, un dépôt

Sprint 1-2 reste simple ; Sprint 3+ suit Clean Architecture

Décision prise en tête de Sprint 3 (voir Livrable_Partie_4_Architecture.md §4.2.9) : pas de refonte rétroactive d'auth/users — un CRUD simple ne gagne pas grand-chose à la séparation. auditLog (S3), referentielTaches (S5-6) et planAnnuel (S7-8) suivent tous les trois le pattern de droite.

SH.04 — inversion de dépendance : le use case ne connaît jamais Drizzle

Pourquoi garder l'ancien pattern pour auth/users

  • CRUD direct, peu de règles métier à isoler
  • 1 dev à temps partagé — 3 fichiers, pas 5, tant que ça suffit
  • Migration possible plus tard, sans urgence

Pourquoi Clean Architecture à partir de S3

  • Logique métier dense (charge agrégée, snapshots, machine à états)
  • Use cases testables sans Postgres (98 tests unitaires cumulés, 0 DB)
  • Port remplaçable sans toucher la règle métier
SH.05 Flux réel — connexion + 2FA

Le chemin le plus complet construit à ce jour

Login, verrouillage anti brute-force, 2FA email OTP et écriture dans le journal d'audit (Module 16, Sprint 3) — le tout vérifié par tests d'intégration sur base Postgres réelle, pas mocké.

SH.06 — durées indicatives (2 semaines/sprint), pas des dates engagées

Point de vigilance (§7.3.2) : Synthèse DAI (Module 14) agrège presque tous les autres modules — il ne peut raisonnablement être construit qu'en dernier.
